The Regulated Frontier

Turning DSH from read-only into a place people actually trade.

Everything today is read-only or paper. Real execution is a deliberate, gated build — not a flag flip. This lays out the flow, the safety stack, what has to be built, the compliance questions, and the decisions only you can make.

Where you are today

One string is all that separates the app from live orders — and that's the problem.

SnapTrade is linked as connectionType: "read" (snaptrade.server.ts:127). Positions and balances flow in; nothing goes out. The "Managed," "AI Funds," and "Day Trader" engines execute against database rows at the last quote — no broker, no real capital. That's a safe, honest starting point. But it means "go live" is often imagined as flipping read → trade, and it is emphatically not: that flag with no gates around it is how people lose money and you inherit liability. The rest of this document is the scaffolding that has to exist before that flag ever changes.

The execution flow

What a single live order actually has to do.

1

Order ticket

User specifies symbol, side, quantity (or notional), order type (market / limit), and time-in-force. Client-side validation only — nothing is trusted yet.

new UI · none exists today
2

Pre-trade checks (server)

Re-validate everything server-side: market hours, buying power vs. the synced balance, position limits, symbol tradability, PDT/day-trade count, and per-user risk caps. Reject before touching the broker.

new server layer
3

Impact preview

Call SnapTrade POST /trade/impact to get estimated price, fees, and buying-power effect. Show the user a review screen with the real numbers. Nothing is placed yet.

SnapTrade trade API
4

Explicit confirm → place

User confirms the previewed order. Server places it (POST /trade/{tradeId}) with an idempotency key so a double-tap or retry can't duplicate the order.

idempotent · audited
5

Status & fills

Poll or webhook order status until filled / partially filled / rejected / cancelled. Persist every state transition. Surface it live in the UI; allow cancel of working orders.

reconciliation
6

Reconcile

Replace the current "fill at last quote" assumption with the broker's actual fill price and fees. Update positions, cash, and the audit log from truth, not estimate.

truth over estimate

The safety stack

Layers between "tap" and "real money leaves."

01

Feature flag + per-user opt-in

Live trading off by default, globally and per user. A user must explicitly enable it and re-consent SnapTrade with trade scope — separate from the read-only link they have now.

02

Server-side authority

Every order validated and placed server-side under the user's own auth. The client never talks to the broker directly and can never be the source of truth for buying power or limits.

03

Explicit review + confirm

No order places without the user seeing the impact preview and confirming. No "one-tap trade" at launch.

04

Risk limits & kill switch

Per-order and per-day notional caps, max position size, and a global kill switch that halts all order routing instantly if something looks wrong.

05

Idempotency & audit trail

Every order carries an idempotency key; every state change is logged immutably (who, what, when, which key). This is both a safety and a compliance requirement.

06

Hard separation of paper vs live

Paper and live accounts never share a code path that could cross wires. A live order is visually and structurally unmistakable from a simulated one.

Compliance landscape

The honest flags — read before writing any execution code.

I'm not a lawyer and this isn't legal advice. But the shape of the regulatory questions is predictable, and which ones apply depends almost entirely on the first decision below — whether users place their own orders, or the app/AI places orders for them.

  • Self-directed vs. discretionary. If each user places their own orders through their own linked broker, you're a software front-end over a regulated broker (SnapTrade + the executing broker carry most of the burden). If the app or an AI decides and places trades on someone's behalf, that's discretionary asset management — likely RIA and/or broker-dealer territory, with registration, suitability, and fiduciary duties.
  • AI-driven allocation raises the bar. The "Managed" and "AI Funds" engines currently pick trades with an LLM. Pointing those at real money is the single biggest compliance escalation in the whole project — suitability, best-execution, and advice-giving all attach.
  • Disclosures & agreements. Risk disclosures, terms of service, and clear "this is not investment advice" labeling — especially anywhere AI output sits next to a trade button.
  • Pattern Day Trader & margin rules. If day-trading features touch real accounts, PDT ($25k equity) and margin rules must be enforced or surfaced.
  • Data & credential handling. Trade-scoped broker credentials are far more sensitive than read tokens. (Already flagged: the SnapTrade user_secret should be server-only — fixed in the multi-user PR.)
  • Record-keeping. Order audit trails and communications may need retention regardless of registration status.

Recommended path

If it were mine, this is the sequence.

A

Full flow on paper

Ticket → preview → confirm → status → reconcile, wired to the existing paper engine. All the safety gates, zero real-money risk.

B

Self-directed pilot

Swap the adapter to SnapTrade trade scope for a tiny allowlist of users, equities + market/limit only, hard caps + kill switch.

C

Broaden carefully

Widen access, add order types, tighten reconciliation and monitoring. Still self-directed.

D

(Only if you choose) automation

Real discretionary AI trading — gated behind the registration/compliance work Decision 1 implies. A separate, deliberate program.

My recommendation: commit to self-directed (Decision 1) and paper-parity first (Decision 2). It gets people real trading through their own brokers with the smallest legal surface, reuses the entire flow you'd need anyway, and keeps the AI as an advisor rather than a discretionary manager — which is where the heavy regulation lives. You can always escalate later; you can't easily un-route a bad automated order.
