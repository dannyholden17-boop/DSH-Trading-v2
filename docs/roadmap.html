Executive summary

You're ~75% of the way to the product you described — but two structural gaps must close first.

The good news: this is a real, substantial application, not a demo. Thirty-five routes, a proper Supabase backend with Row-Level Security on every table, live market data (Finnhub + Yahoo), read-only brokerage linking through SnapTrade, AI research and paper-trading "funds," and a backtesting engine wired to real historical prices. The bones of a serious trading terminal are here.

The two gaps that define the work ahead: (1) the core screens are single-tenant — everyone shares one portfolio and watchlist — so "multiple people, each with their own reports" isn't true yet; and (2) nothing places a live trade — every "trade" is simulated. Neither is a flaw in the vision; both are the natural next build phase, and both are very achievable.

Correction to my first read: I initially warned that the committed .env meant "rotate every key." After reading it, that was an over-alarm. The committed .env holds only public values (Supabase URL, project ref, and the publishable/anon key that ships to the browser anyway). No service-role key and no third-party API keys are committed — those stay server-side at runtime. It's still worth untracking, but it is not an emergency.

Assessment · four domains

Graded against what a production version needs.

01

Multi-user & reports

NEEDS WORK
  • Single-tenant bug (top priority). Dashboard, Portfolio, Watchlist, Settings & AI Reports run on the RLS-bypassing service-role client and read one global row — every user shares the same data.
  • No auth gate on those endpoints — effectively reachable without a token.
  • No roles / teams / orgs. No structure yet for "multiple people collaborating."
  • Auth itself is sound: Supabase email/password + Google, tokens verified server-side.
  • Notes, chat, accounts, managed portfolios are correctly per-user.
02

Live trading

READ-ONLY TODAY
  • No real order execution anywhere. SnapTrade is linked as connectionType: "read" — positions sync in, nothing goes out.
  • "Managed," "AI Funds," "Day Trader" are paper. Fills book against database rows at the last quote — no spread, slippage, or market-hours checks.
  • The safe architecture is already chosen: users link their own broker; the app never custodies money.
  • Clean, disclosed separation — the honest base to build real execution on, deliberately.
03

Backtesting engine

SOLID CORE
  • Real data, correct mechanics. Runs on real Yahoo daily bars; equity curve, drawdown, Wilder-smoothed RSI and rolling SMA are all correct.
  • No transaction costs or slippage — flatters high-frequency configs.
  • Stop-losses fill at the close, not intrabar — the single biggest result distortion.
  • No Sharpe, no benchmark. "3 strategies" is really one strategy with three presets.
04

Security & secrets

MOSTLY SOUND
  • RLS enabled on every table, per-user tables scoped to auth.uid().
  • No catastrophic secrets committed; third-party & service-role keys stay server-side.
  • Public cron hooks gated only by the public anon key — anyone could trigger expensive LLM/trading jobs. Top fix.
  • SnapTrade user_secret is browser-readable — should never leave the server.
  • .env is tracked in git (public values only) — untrack it.
